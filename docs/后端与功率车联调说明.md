# Pad、共用后端与功率车模拟器联调说明

## 已验证链路

2026-08-26 使用模拟患者 `1006` 完成端到端验证：

```text
模拟器 http://47.94.149.175:3000
  → 接收端 http://123.57.205.29:4000
  → 共用后端 http://123.57.205.29:8000
  → 云库 exercise_records / exercise_details
  → WebSocket /ws/watch/10001_1006
  → Pad
```

测试生成记录 `1006_20260826_231218`，后端成功聚合为 20 分钟训练并保存 239 个有效采样点。实时消息包含心率、收缩压、舒张压、速度、距离、功率、阻力、热量、血氧和训练阶段。

## 模拟器配置

- 接收端地址：`http://123.57.205.29:4000`
- 医院 ID：`10001`
- 用户 ID / 登录码：与模拟数据患者短号一致，例如 `1006`
- 设备 ID：`bike-sim-001`
- 传输协议：实时逐条（HTTP REST）
- 常规发送间隔：`5000 ms`

Pad 输入同一个短号 `1006` 后会从患者库映射到完整 ID `10001_1006`，并订阅该完整 ID 的实时通道。模拟器界面的 SSE 只是模拟器自身状态日志，不是 Pad 的实时数据协议。

## 数据单位

- `speed`：km/h
- `distance`：后端实际为米，Pad 展示时除以 1000 转为 km
- `power`：W
- `heart_rate`：bpm
- `spo2`：%
- `calories`：kcal
- `systolic_bp` / `diastolic_bp`：mmHg

## 需要后端同事确认或补充

1. 提供 Pad/患者专用登录接口。当前 `/api/auth/login` 对患者短号 `1006` 返回“登录码无效”，不能在 App 内获得正式 token。
2. 提供“训练上下文”接口，一次返回患者信息、当前有效且已签署处方、处方周期状态和训练准入结果，避免 Pad 分散调用医护接口。
3. 明确处方 `plan_data` 的稳定 JSON Schema，至少包括运动类型、热身/训练/放松时长、靶心率、目标功率、阻力、RPE 和停止条件。
4. 补充踏频字段。当前模拟器消息和 `exercise_details` 均无 cadence；可新增列，或约定写入 `extra_data.cadence` 并在 WebSocket 中广播。
5. 明确 WebSocket 是否需要 token、心跳和断线续传；当前 `/ws/watch/{patient_user_id}` 可直接连接。
6. 单次训练数据继续由 `exercise_records + exercise_details` 作为唯一真源；Pad 不另建报告表。阶段报告由 Web 报告管理生成，本期 Pad 不实现。
7. 为正式 App 域名或网关配置 CORS 及 HTTPS/WSS。当前 FastAPI 会拒绝 `localhost` 和 `capacitor://localhost` 的跨域预检；开发环境已用 Vite 代理，Android 已用 Capacitor HTTP 绕开浏览器 CORS，但正式环境仍建议在后端明确放行来源。

## 建议的训练上下文接口

```http
POST /api/pad/training-context
Authorization: Bearer <pad-token>
Content-Type: application/json

{"hospital_id":"10001","record_number":"1006","device_id":"bike-sim-001"}
```

建议返回：

```json
{
  "patient": {"user_id":"10001_1006","patient_id":"1006","full_name":"李国立"},
  "prescription": {"id":123,"status":"completed","plan_data":{}},
  "admission": {"allowed":true,"reason":null},
  "realtime": {"watch_path":"/ws/watch/10001_1006"}
}
```
